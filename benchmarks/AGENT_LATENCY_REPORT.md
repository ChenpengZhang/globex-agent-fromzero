# Agent 并行检索延迟试验报告

运行日期：2026-09-13。测试对象：`text-embedding-v4`（1,024 维）与 10,000
件 Amazon ESCI 商品组成的 Top-50 精确余弦检索。

## 结论

- 15 个配对样本中，串行平均耗时为 **1,324.5 ms**，并行平均耗时为
  **620.1 ms**。
- 按全部请求总耗时计算，并行原型是串行代理的 **2.14 倍**，即延迟下降
  **53.2%**。
- 每个配对样本等权时，平均延迟下降 **50.2%**；95% 配对 bootstrap 区间为
  **32.6%–66.1%**。
- 配对加速倍数的中位数为 **2.91 倍**。该数字更接近接口没有明显长尾时的
  典型体验，但正式汇报建议采用更保守的 2.14 倍总体结果。

## 五组场景

每组运行三轮，表中展示该组串行和并行耗时的中位数（p50）。

| 场景 | 独立搜索分支 | 串行 p50 | 并行 p50 | 加速 | 延迟下降 |
|---|---:|---:|---:|---:|---:|
| 露营装备 | 4 | 1,232.8 ms | 909.6 ms | 1.36x | 26.2% |
| 乔迁礼物 | 3 | 904.8 ms | 328.5 ms | 2.75x | 63.7% |
| 夏季旅行用品 | 4 | 1,377.8 ms | 367.8 ms | 3.75x | 73.3% |
| 商务旅行电子产品 | 4 | 1,340.3 ms | 385.3 ms | 3.48x | 71.3% |
| 轻装旅行 | 3 | 1,014.9 ms | 388.9 ms | 2.61x | 61.7% |

## 公平性与异常

串行代理和并行原型执行完全相同的 18 个查询分支。每个分支均单独请求真实
embedding 接口，再在同一份 10k 商品矩阵上做 Top-50 搜索；两种模式只改变
分支的调度方式。每轮交替先运行串行或并行，减少连接预热和运行顺序偏差。

完整试验应有 109 次接口请求（包括一次预热），实际发生 111 次，说明充值权限
同步期间出现了两次 403 重试。并行模式受最慢分支支配，因此两个配对样本分别
出现 0.89x 和 0.79x 的暂时倒退。报告没有删除这些异常点，2.14x 的总体结果
已经包含它们。

## 结果边界

这是一项真实“检索执行层”并发试验，不是当前应用的端到端 Agent 延迟结论。
它没有计入 MainAgent 的需求拆解、MainAgent/SearchAgent 模型调用、reranker 和
最终答案合成。

更重要的是，当前应用只有专家 Agent 派发，尚无显式的多任务并行编排：
`task_dispatch` 会等待一个专家完整回复，项目文档也把多派发并行列为当前限制。
因此本报告量化的是把独立检索分支并行化后的可实现收益，而不是声称现有核心
代码已经得到该收益。全部试验代码位于 `benchmarks/`，没有导入或修改 `app/`。

## 复现

```bash
cd benchmarks
PYTHONPATH=. .venv/bin/python -m src.run_agent_latency_benchmark \
  --data-dir data/processed_pilot_10k \
  --top-k 50 \
  --repeats 3 \
  --backend live
```

机器可读结果位于 `results/agent_latency/summary.json`，15 个配对样本的原始数据
位于 `results/agent_latency/runs.csv`。
